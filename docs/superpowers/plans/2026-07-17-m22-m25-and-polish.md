# M22–M25 + Polish Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Land uncommitted M18/M19 polish + M21 range routing, then deliver production-path M22 (rebalance/merge/placement), M23 (cross-shard 2PC), M24 (encryption-at-rest + prefix ACL), and M25 (ecosystem/scale-proof close-out) so the Distributed Transactional KV arc can exit toward v0.2.0 evaluation.

**Architecture:** Build on multi-raft + epoch’d `StaticRangeTable` (M20/M21). M22 adds merge, leadership transfer, learner→promote, and a simple store balancer. M23 introduces a coordinator-driven 2PC over per-group Raft (`TxnPrepare`/`TxnCommit`/`TxnAbort` records). M24 wraps Disk with AES-GCM and enforces per-prefix ACLs on the client path. M25 closes clients, conformance, and gates.

**Tech Stack:** Rust workspace (`kaya-*`, `kayactl`), Go client (`clients/kaya-go`), optional TS client (`clients/kaya-ts`), specs under `spec/docs/`, Jepsen under `crates/kaya-jepsen-test`.

**Worktree:** `.worktrees/feat-m22-m25` on branch `feat/m22-m25-and-polish`

## Global Constraints

- Correctness-first: every feature ships with unit and/or integration tests; no production-readiness claim beyond what tests prove.
- Spec → implement → test → CHANGELOG/ROADMAP sync per milestone close-out task.
- Wire opcodes are stable: never renumber existing opcodes; allocate new ones sequentially after 16 (`SPLIT_RANGE`).
- Shared-engine multi-raft: ranges are routing partitions; physical key migration is out of scope unless a task explicitly requires it.
- No SQL, no multi-tenancy beyond per-prefix ACL, no geo-replication.
- Keep public APIs backward compatible where possible (HELLO PROTO_VERSION stays 1 unless a task bumps conformance vectors).
- Commits: conventional commits (`feat:`, `fix:`, `docs:`, `test:`); do not push unless asked.
- Validation baseline (run after each task that touches Rust):
  ```bash
  cargo fmt --all -- --check
  cargo test -p <touched-crates> -- --test-threads=1
  ```
  Full workspace (before milestone close-out commits):
  ```bash
  cargo test --workspace --exclude kaya-jepsen-test -- --test-threads=1
  ```

**Files:**

- Modify: `spec/docs/range-routing-spec.md`
- Test: unit tests in `multi_raft.rs`; IT in `integration_tests.rs`

**Interfaces:**
- Consumes: `StaticRangeTable::split_at`, LIST/SPLIT opcodes 15/16
- Produces:
  - `StaticRangeTable::merge_with_next(left_start: &[u8]) -> Result<StaticRange, String>`
  - Opcode `MERGE_RANGE: u8 = 17`
  - Request: `left_start_len(u32 LE) | left_start`
  - Response: single merged descriptor (same encoding as one LIST_RANGES entry)
  - `kayactl range merge <left-start-hex-or-utf8>`

- [ ] **Step 1: Failing unit test for merge**

```rust
#[test]
fn merge_with_next_recombines_split_ranges() {
    let mut t = StaticRangeTable::single_group(GroupId(0));
    t.split_at(b"m").unwrap();
    assert_eq!(t.ranges().len(), 2);
    let merged = t.merge_with_next(b"").unwrap(); // left starts at empty
    assert_eq!(t.ranges().len(), 1);
    assert!(merged.end_key.is_empty());
    assert_eq!(t.meta_epoch(), 3); // start 1 + split + merge
}
```

- [ ] **Step 2: Implement merge**

Rules:
1. Find range `L` with `start_key == left_start`.
2. Right neighbor `R` must exist and be adjacent (`L.end_key == R.start_key`).
3. Merged range keeps `L.group_id`, `L.range_id`, `epoch = max(L.epoch,R.epoch)+1`, `end_key = R.end_key`.
4. Drop `R` from table; bump `meta_epoch`.
5. Do **not** remove the Raft group process-wide in this task (orphan group idle is OK; document follow-on). Optional: if `ensure_group_hosted` path exists, leave group in host.

- [ ] **Step 3: Wire opcode 17 + server dispatch + kayactl + tests**

- [ ] **Step 4: Commit**

```bash
git commit -m "feat(range): M22 merge_with_next and MERGE_RANGE opcode"
```

### Task 10: Transaction coordinator (multi-group)

**Files:**
- Create: `crates/kaya-server/src/cluster/txn_coord.rs`
- Modify: client_ops TXN_COMMIT path: if mutations span >1 group, run 2PC instead of single-group TxnCommit
- Test: IT with static two ranges, multi-key txn across split point

**Interfaces:**
- Produces:
  ```rust
  pub async fn commit_cross_group(
      /* host, engines or propose hooks */,
      txn_id: u64,
      mutations_by_group: HashMap<GroupId, Vec<(Vec<u8>, Option<Vec<u8>>)>>,
  ) -> Result<(), String>;
  ```
- Algorithm:
  1. Pick coordinator_group = group of lexicographically smallest key.
  2. Parallel propose `TxnPrepare` on each participant; wait applied.
  3. If all prepared, propose `TxnCommit2pc` on all; else `TxnAbort2pc` on prepared participants.
  4. Crash recovery (minimal): on startup scan `\x00txn/rec/*` in Preparing → abort; Prepared without global decision → abort (conservative).

- [ ] **Step 1–4:** Implement + IT `test_cross_range_txn_commit`, commit.
